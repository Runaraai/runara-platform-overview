Harness-Aware Serving: Implementation Plan

1. The outcome

A customer connects their existing agent to one Runara model endpoint. Runara chooses a suitable measured hardware configuration, then routes the agent's repeated requests to a healthy model replica that can reuse previous calculations. We measure whether this actually improves response speed and operating cost.

The first release belongs in Optimizer → Deploy → Deployments, with examples in Docs and actual measurements in Usage. No additional top-level tab is needed. Hosted models continue to work through their current path; they are a later adoption target, not the first rollout.

First milestone: one opt-in dedicated GCP deployment, one pinned model/runtime, two independent replicas on one VM, and a repeatable comparison between ordinary load balancing and session-aware routing. The deployment must remain usable and correctly metered when cache reuse is unavailable.

Do not begin with: a new multi-cloud orchestrator, all models, a custom KV-cache storage system, automatic cross-hardware cache movement, or a promise that bursts never queue.

4. Data flow and component boundaries

Convex manages desired configuration and durable billing, not per-token routing. Inference requests and streaming responses stay on the serving infrastructure — no Convex write on each generated token, and no synchronous full-database scan per request.

Vercel remains the frontend and current app/API integration layer. The production agent endpoint must not depend on a long-running Next.js request to make replica-selection decisions.

Router failure behavior: mark the pilot unhealthy or use an explicitly configured healthy ordinary-routing fallback. Preserve authentication and metering in either path. Never bypass admission to keep the endpoint apparently available.

5. Phased implementation

Owners below are proposed responsibilities, not assigned people. Effort and dates should be estimated after Phase 0 identifies compatibility gaps.

Phase 0 — Freeze the experiment and verify compatibility

  • P0.1 Record the source commit, catalog ID, exact checkpoint revision, engine image digest, GPU edition/count, tokenizer/chat template, parser flags, context size and cache configuration.
  • P0.2 Verify the candidate checkpoint and runtime artifact are complete and accessible in GCS/GCP; verify engine capability locally or in a bounded compatibility job.
  • P0.3 Choose and pin the router adapter after comparing upstream options. Verify it actually supports this engine version, not just the same engine family.
  • P0.4 Establish a replay fixture: multi-turn conversation, tool-result gaps, shared system prompts across distinct sessions, growing history and four-way helper-agent fan-out.
  • P0.5 Specify primary metrics and run conditions before tuning: same model/GPU count/precision, deterministic request schedules, warm-up, cache state, workload seed, repeated runs and held-out sessions.
  • P0.6 Set pilot runtime/cost limits and an independent cleanup deadline. Confirm no customer resources will be adopted into the pilot.

Phase 1 — Define the serving contract and isolation

  • P1.1 Add an explicit harness_aware_serving feature flag with a false fallback and a pilot organization allowlist.
  • P1.2 Define an optional versioned servingPolicy on the deployment: mode, policy version, runtime/recipe identity, replica topology, routing policy, queue/deadline limits and experiment evidence ID.
  • P1.3 Document X-Runara-Session-Id: optional opaque bounded identifier, stable across one agent conversation; a separate ID for each helper conversation.
  • P1.4 Namespace affinity by authenticated deployment/tenant and runtime identity. The header is a routing hint, never authorization.
  • P1.5 Define supported endpoints and fields: chat completions, model listing, tools/tool results, reasoning controls, JSON responses and streaming.
  • P1.6 Define behavior for invalid sessions, overload, request cancellation, engine failure and router restart.

Phase 2 — Provision an isolated two-replica pilot

  • P2.1 Extend the optimizer startup generator through an opt-in branch; preserve the default least_conn path.
  • P2.2 Install a pinned local routing service between the existing authenticated proxy and the replica ports.
  • P2.3 Enable native prefix caching only on the new verified recipe. Never silently alter the measured launch command of an existing catalog row.
  • P2.4 Health-check each engine and perform an actual model request before admitting it.
  • P2.5 Preserve bounded capacity search, startup deadline, cancellation and losing-resource cleanup.
  • P2.6 Ensure Stop drains admissions and in-flight usage, takes the final meter sample, and tears down router, engines and VM.

Phase 3 — Session-aware routing and safe overload behavior

  • P3.1 Add a stable session-affinity policy behind an adapter. Deterministic rendezvous hashing over healthy stable replica IDs is an acceptable minimal fallback.
  • P3.2 Preserve affinity only within a bounded queue/deadline budget. An overloaded replica may spill to another healthy replica; record this as a possible cold-cache fallback, not a cache hit.
  • P3.3 Exclude unhealthy/draining replicas. Allow a surviving replica to recompute the prompt after failure.
  • P3.4 Preserve immediate SSE delivery, tool-call deltas, reasoning content and cancellation.
  • P3.5 Keep cache compatibility keys tied to checkpoint, tokenizer/template, precision, engine/KV layout, adapter and relevant launch configuration.
  • P3.6 Bound request bodies, queues and diagnostic state.

Phase 4 — Telemetry and billing correctness

  • P4.1 Add request-level queue time, TTFT, end-to-end latency, errors and output rate. Distinguish p95/p99 TTFT, p90 request-mean TPOT and p99 individual ITL.
  • P4.2 Add engine-confirmed cached/uncached prompt-token observations, cache capacity/evictions where exposed, routing policy, replica health and spillover counts.
  • P4.3 Audit the exact engine version's counter semantics. Determine whether prompt counters include cached tokens.
  • P4.4 Keep one billing authority: existing dedicated cumulative meter and ledger. Routing observations are analytics, not a second invoice.
  • P4.5 Cover replica restart, counter reset, unreachable replica, cancellation, partial stream and final drain.
  • P4.6 Send bounded interval aggregates to Convex; keep detailed latency histograms in monitoring.
  • P4.7 Show provider operating cost separately from customer wallet charges.

Phase 5 — Benchmark against a strong baseline

ArmPurpose

  • P5.2 Use at least three independent runs per key cell and held-out sessions. Record per-run distributions and uncertainty.
  • P5.3 Validate full agent task completion, tool-call format/arguments and reasoning behavior.
  • P5.4 Measure actual GPU-hours and all attributable router/CPU/storage/network costs per completed workload.

  • P5.6 Verify import failure leaves existing optimizer data usable.

Phase 6 — Opt-in beta in existing screens

  • P6.1 Optimizer: expose an agent workload only when an eligible measured profile exists.
  • P6.2 Deploy dialog: show actual hardware, replica count, serving policy, supported cloud and frozen billing quote.
  • P6.3 Deployments: retain current lifecycle and failure display; add active policy, ready/total replicas, observed cache reuse, latency/queue metrics.
  • P6.4 Docs: show a working HTTP example with a stable session header, no-header fallback, helper-session guidance.
  • P6.5 Usage: show actual wallet spend and request/token measurements. Label experiment-derived savings separately.
  • P6.6 Canary to an internal organization, then one willing pilot customer; collect feedback before any general enablement.

Phase 7 — Cache offload and capacity management (after pilot)

  • P7.1 If cache eviction during tool gaps is a material cost, evaluate a compatible LMCache/upstream backend.
  • P7.2 Add storage quotas, encryption/access boundaries, TTL/deletion and a tested cold-recompute fallback.
  • P7.3 Introduce a logical serving pool and replica registry across VMs/pods.
  • P7.4 Redesign meter membership with immutable replica identities, last-sample acknowledgements and idempotent removal before autoscaling.
  • P7.5 Add queue-based autoscaling with min/max replicas, cooldowns, budget caps, actual model warm-up estimates.
  • P7.6 Begin reactive scaling plus an explicit warm reserve.
  • P7.7 Design router high availability and consistent affinity/membership.

Phase 8 — BYOC, additional engines/hardware and Hosted models

  • P8.1 Add GCP BYOC using the same signed/validated policy, private networking and least-privilege access.
  • P8.2 Extend to AWS after revalidating VM topology, runtime, storage, pricing and drain behavior.
  • P8.3 Qualify SGLang separately. Preserve AMD/ATOM and TPU catalog paths.
  • P8.4 Adapt Hosted models separately using their request journal, tenant-safe cache boundaries and GKE lifecycle.

Durable state versus transient state

  • Deployment: optional policy version, evidence ID, exact model/runtime, selected topology and rollout state. Absent fields mean legacy mode.
  • Policy/release metadata: immutable configuration and experiment provenance; select through an explicit activation operation.
  • Aggregates: bounded deployment/time buckets for request counts, cache-token quantities, latency histograms, spillovers and observed infrastructure cost.
  • Transient routing: local or upstream-managed replica health and affinity; bounded, reconstructible and not authoritative for money.
  • Billing: existing ledger/cursors remain authoritative. Schema migration must not reinterpret historical usage or quotes.

Before adding a table, check whether the existing deployment/usage model can hold a backwards-compatible field. Do not put prompts, raw API keys or unbounded session histories in Convex.

8. Release gates and rollback

Required before beta

  • Exact checkpoint/image/hardware and changed cache/router recipe recorded and tested.
  • No cross-deployment/session authorization leak; identical client session IDs cannot cross tenant boundaries.
  • No unsupported change to model outputs, tool-call formatting or reasoning behavior.
  • Both streamed and non-streamed requests work; slow clients and disconnects cannot exhaust the gateway.
  • Request accounting reconciles across replica restarts, retries, missing usage and drain; no guessed or duplicate charges.
  • Startup and cloud capacity failures terminate with a useful deployment-specific reason; Stop cannot leave paid orphan resources.
  • Metrics distinguish cache affinity, actual reuse, queueing and missing observations.
  • Held-out comparison is reproducible; operating-cost claims include warm capacity and added infrastructure.
  • CI, build, preview smoke and real-cloud pilot checks pass.

Rollback procedure to implement and rehearse

  1. Disable admission of new harness-aware deployments for the pilot organization. This must not silently mutate active tariffs or kill running streams.
  2. For a running affected deployment, drain and switch through an explicit operation to healthy ordinary routing on the same verified engines, or stop it safely if a fallback is unavailable.
  3. If changing cache flags requires engine restart, perform it as a controlled rollout; flag changes alone cannot safely apply runtime settings.
  4. Retain existing billing journals/cursors and evidence. Mark lost cache as cold; never invent recovered usage or replay generation automatically.
  5. Remove experiment-owned cloud resources and verify the resource list is empty. Re-enable only after the regression has been reproduced and tested.
