Harness-Aware Serving

Bring your agent and your model. Runara runs them on the cheapest hardware that works, without redoing work already done — whether that work is serving, fine-tuning, or generating rollouts.

01 The problem

Runara runs the model. The customer brings the agent software around it, called the “harness.” That's a smaller market than selling everything. This document explains that limit, why it's still the right place to start, and leaves open whether we build a harness later.

Today the big AI labs sell everything as one package: the agent software, the model and the hardware. One vendor, one bill, already connected to the customer's data. We call this the bundle. Adam estimates about 95% of the money in this market goes to it (his estimate, not yet sourced). The open alternative looks like phones before one company owned the whole stack: agent software from one company, model from another, hardware from a third. Someone has to connect those pieces, and whoever does pays a cost the bundled vendors don't.

For now, we do one thing on purpose: we pick the hardware and run the model on it. The customer must already have a harness, so we can only sell to companies that have built one. Enterprises that want the full bundle have nowhere to plug us in. Reaching them would mean building connectors to Office, Google Workspace and similar tools, each one its own project. Whether and when we build a harness is still an open team decision (see section 12).

02 Definition

The harness is the software wrapped around a model that turns it into an agent: its instructions, the tools it can use, the loop that calls those tools, how it manages memory, how it launches helper agents, and its connections to other systems. Claude Code, Cursor, Devin and OpenHands are harnesses. Runara doesn't build one. We run the traffic a harness sends.

HarnessControl plane (Runara)
DecidesWhat to compute — prompts, tools, stepsWhere and how to run it — which chip, which serving software, how the model is compressed and split, and where each request goes
SeesTask meaningRequest logs, performance data, prices, and promised response times (SLAs)
OptimizesTask successCost per token, at the speed the customer needs
OwnerCustomerRunara

The two do different jobs. They connect through a standard API in the same format OpenAI uses, so switching to us is easy.

03 System architecture — inference

The harness talks to one address. Behind it, Runara makes two kinds of decision: which hardware runs the model, and how the traffic runs on it. That means sending each conversation back to the server that already remembers it, keeping that memory during pauses, and having spare servers ready before a burst arrives.

The harness doesn't see any of this. It sends every turn to the same address it always has. Behind that address, Runara does four things:

  • Hardware is chosen, not assumed. We don't default to the newest, most expensive GPU. We test which chip is the cheapest one that's still fast enough for the customer, at their prices. Often that's an older one. Everything below then gets more out of that hardware.
  • The router sends each conversation back to the same server. An agent conversation has many turns, and each server remembers the conversations it has already worked on. So we read a conversation ID from each request and keep sending that conversation to the same server, instead of to whichever server is least busy. A new conversation goes wherever there's room.
  • The scheduler keeps conversation memory alive. The scheduler is the part that decides what goes where. While the agent pauses to run a tool, an ordinary server throws away its memory of the conversation (the “KV cache”) to free up space. We keep it: in place for a short pause, or moved to cheaper storage (CPU memory, SSD or shared storage) for a longer one. When the agent comes back, nothing has to be redone.
  • The autoscaler plans for bursts. When an agent launches several helper agents at once, many requests arrive together, unlike the usual random trickle of traffic. We recognize that pattern and have spare servers ready beforehand, so the helpers don't wait in line.

What we build vs. what we use

Free open-source tools already do much of the basic work: NVIDIA Dynamo, llm-d, SGLang's router and LMCache can route by conversation memory and move that memory to cheaper storage. We build on them instead of rebuilding them, and we don't build our own storage. Our part is the decisions they don't make: which hardware to use, where each conversation and its memory should live, and what that costs, measured on the customer's own traffic.

04 Example

One coding-agent conversation, turn by turn, run by Runara. Below it, the same conversation on an ordinary setup for comparison.

StepHarness doesRunara doesEffect
1. Cold startSends its instructions, tool descriptions and the first message (~8K tokens)Router picks a free server; the model reads the whole input from scratchNothing remembered yet, so all 8K input tokens cost full price
2. Tool callCalls a file-read tool, waits ~6s for the resultScheduler keeps this conversation's memory on the server during the pause instead of throwing it awayNothing to redo when the agent comes back
3. Turn 2Resends the full history (~8.2K tokens) + tool result + next messageRouter sends it to the same server; only the ~400 new tokens need reading~95% of this turn's input is already remembered
4. Turns 3–43Same pattern repeats as history keeps growingSame server, growing memory; the share already remembered climbs toward the ~96% medianCost per turn stays about flat, instead of growing with the length of the conversation
5. Sub-agent burstLaunches 4 helper agents at once for a multi-file taskAutoscaler already has spare servers ready, so the 4 new conversations don't wait behind the main oneThe helpers respond about as fast as a single conversation would

Without harness-aware serving

An ordinary load balancer sends turn 2 to whichever server is least busy, which usually isn't the one that remembers this conversation. So all ~8.2K tokens get read again, every turn, for the whole conversation. The helper-agent burst waits in line behind everything else, because nothing planned for it.

This example keeps the hardware the same to show the serving effect alone. In practice the two add up: the right chip makes every token cheaper, and smarter serving means fewer tokens need processing at all.

05 Why it matters

The harness shapes the traffic, and the traffic decides the cost. We don't need to build a harness to benefit from understanding one. We need to run harness traffic better than anyone, on the right hardware.

Almost all the input has been seen before

Every turn, a harness sends the whole conversation again: instructions, tools, history, then the new message. Most of it can be remembered from the last turn instead of processed again.

43median turns per agent session fact
142Kmedian input tokens per session fact
>96%of input already remembered (cache hit rate) fact
30×price gap, new vs. remembered input (DeepSeek: $0.044 vs $1.32/M) fact

Source: SemiAnalysis AgentX, which replays 393 real Claude Code sessions; DeepSeek's published list prices.

If 96% of input is already remembered, input costs about $0.095 per million tokens. At 80%, it's about $0.30, roughly 3× more (simple math on the list prices above). Every point of cache hit rate is money, and keeping it high takes serving that understands the harness.

Inference wastes money in three ways: the wrong chip, the wrong settings, and doing the same work twice. Smarter serving fixes the third. Choosing the hardware fixes the first.

Software alone moves revenue 1.8–2.7× on identical hardware

On SemiAnalysis's published agent benchmark (Sep 2026), changing only the serving software raised revenue per gigawatt 1.8× on GB300 and 2.7× on B200 fact. Much of that difference comes from how well the software handles agent traffic: remembering, moving memory to cheaper storage, and scheduling. How much of it our stack captures is still a claim — P45 below is the test.

Getting answers right matters as much as speed

Open models expect specific message and tool-call formats. Get the format, the tool-call reading or the handling of reasoning text wrong, and the agent quietly breaks. Different providers running the exact same model have shown measurably different tool-call accuracy; Moonshot publishes a checking tool for Kimi for this reason. Compressing a model (quantization) also causes small errors that pile up over a long agent run, which single-question benchmarks miss. So quality has to be tested on real agent runs, not standard tests like MMLU.

Every conversation improves the next hardware choice

Each conversation we run shows how a harness's traffic behaves on a given chip and setup. With the customer's permission, we add those measurements to our performance map, so the next recommendation is better. AI agents can write serving software, but they can't produce measurements from chips they don't run on. That data is the advantage that grows over time.

Not building a harness keeps us neutral

Companies with their own harness (Cognition, Cursor, Character.AI, internal platform teams) are unlikely to buy from a vendor that competes with them hypothesis. The big AI labs compete with them; we don't, today. Because our API uses the standard OpenAI format, any harness can switch to us by changing one address. Enterprises that keep their harness and data in-house (finance, cyber, healthcare) can run Runara inside their own cloud and keep control on their side.

Two caveats. Several of these companies already buy inference from Together AI, so we'd be replacing someone, not filling a gap. And if we build a harness later, we give up this neutrality.

06 A second harness: fine-tuning new in v3

A training loop is also a harness: a loop around the model that decides what to compute next. In fine-tuning, the loop runs data forward through the model (forward pass), works backward to find what to adjust (backward pass), updates the model (optimizer step), and repeats for every batch. Runara's method works the same way here: measure the job, then pick the cheapest hardware and settings that fit it.

The open-source tools

LlamaFactory is well known, but fine-tuning tools change fast and none stays the default for long. Here's the current field as we understand it:

FrameworkWhat it is
LlamaFactoryConfig-driven fine-tuning UI/CLI covering LoRA, QLoRA, full fine-tune and RLHF-style methods across many model families reported
AxolotlYAML-configured fine-tuning on top of HuggingFace + DeepSpeed/FSDP, popular for community LoRA and full fine-tunes reported
torchtunePyTorch-native fine-tuning library, no config-framework layer; recipes are editable Python, closest to the underlying training loop reported
UnslothHand-optimized kernels for LoRA/QLoRA; reports significantly lower memory and faster training on single-GPU setups reported
HuggingFace TRL + PEFT + AccelerateThe library-level building blocks (adapters, trainer loops, distributed launch) most of the above are built on or compatible with reported
NVIDIA NeMo / Megatron-LMProduction-grade large-scale training with tensor/pipeline/sequence parallelism, aimed at frontier-scale full pretraining and fine-tuning reported

We don't need to pick one. Like the serving software in section 03, these tools run the loop itself. Runara's part is measuring what they do on real hardware and choosing the setup underneath them, not replacing them.

Measuring fine-tuning the way we measure inference

For inference, we measure how each model performs on each chip. For fine-tuning, we measure each training step for a given model size, a given way of splitting the work across GPUs, and a given number precision. The forward pass, backward pass and optimizer step are each measured separately for time and peak memory.

Why this is about choosing hardware, not just a training recipe

A full fine-tune, a LoRA fine-tune and a QLoRA fine-tune of the same model aren't three settings of one job. They need very different amounts of memory, so each fits a different cheapest GPU. The profiler measures what a job actually needs, instead of using whatever GPUs the customer already has reserved. It's the training version of section 03's “hardware is chosen, not assumed.”

Where this sits

Fine-tuning can be built sooner than RL rollouts (section 07). The measuring tools are a small extension of what section 03 already needs, and the open frameworks above already define the loop to measure. It still needs its own pilot; P47 below proposes one.

07 A third harness: RL rollouts

A coding agent isn't the only loop wrapped around a model. Reinforcement learning (RL) training is one too, and serving companies already sell rollout generation as a product. It's the natural next market after inference, not something we build in Year 1.

RL training works like an agent harness: a loop around the model that decides what to do next based on what came back. Instead of instructions and tool calls, it uses a batch of prompts, a rule for sampling answers, a reward model that scores them, and a model update, repeated thousands of times. The part that runs on a GPU is rollout generation: producing many possible answers per prompt, at scale, so they can be scored. That's inference traffic, but it looks nothing like a chat conversation.

>70%of RL training time is spent generating rollouts, not training reported

This is Together AI's own figure for its RL product. If most of an RL run is spent generating rollouts, making RL fast is mostly a serving problem, not a training problem.

How rollout generation connects to the training step

Rollout generation uses section 03's serving setup almost unchanged; it's the same kind of work with a different traffic pattern. The training step reuses section 06's profiler. The two meet when updated model weights are sent to the rollout servers (the “weight sync”).

Two of the three split the work the same way Runara does for agents: the training loop (trainer, evaluator, reward model) stays with the customer or a managed layer, and rollout generation, the actual inference, runs on a production serving system underneath. Fireworks' “bring your own trainer” is essentially the same offer as “bring your agent and your model.”

This fits a wider trend. Serving companies like Fireworks and Together are moving into training, and training platforms like Thinking Machines are reportedly moving into serving (unverified). Everyone is heading toward production inference, because that's the spending that comes back every day.

Rollout traffic is a different problem from both agent serving and fine-tuning:

  • Volume matters more than speed. A training run cares about total rollouts per second, not how fast any single one finishes. The goal changes from “fast enough to feel instant” to “as many samples per GPU-hour as possible,” which makes cheaper hardware even more attractive.
  • Many answers at once, not ongoing conversations. Many separate answers are generated from the same prompt at once, then thrown away after scoring. There's no conversation to send back to the same server. Sizing memory matters again here, but for generating rather than training.
  • The model keeps changing. The model being served changes after every training step. Serving has to load the new weights regularly (every few seconds to a minute, per Together's numbers) without stopping the rollouts already running.

Where this sits

Year 1 focuses on inference and fine-tuning. Rollout serving goes into the investor story as the next market. One test we can run now: ask a training platform whether they'd build rollout serving themselves or pay for it.

09 BYOC deployment

Everything above assumes Runara runs a group of servers with a router in front. Bring-your-own-cloud (BYOC), where we run inside the customer's own cloud account, changes who owns those servers, not whether the techniques work. There's one real exception.

Sending conversations back to the same server and keeping their memory during pauses only involve one customer's own traffic. They work just as well, or better, inside the customer's cloud, since no other customers compete for the same servers. Enterprises that keep their harness and data in-house (finance, cyber, healthcare) get the same benefits without their data leaving their own systems. That's the reason to offer BYOC.

Handling bursts is the exception. On Runara's shared servers, one customer's burst is evened out by everyone else's traffic, so keeping spare capacity is cheap. Under BYOC, spare capacity covers only that one customer. Handling a burst then means either the customer pays for idle servers (which weakens our cost pitch), or Runara starts new servers in the customer's account when needed. Starting a server and loading the model usually takes minutes, but a helper-agent burst needs capacity in seconds.

We need an answer before promising this under BYOC. Either we keep spare servers ready for each customer, possibly on cheaper or older GPUs since much helper-agent work is routine hypothesis, or we clearly tell customers that bursts respond more slowly under BYOC than on shared servers.

10 Roadmap

Phase 1

Harness-aware serving on the right hardware

Pick the cheapest hardware that meets the promised speed, then run agent traffic smartly on it: sending conversations to the right server, keeping their memory, and handling bursts. Built on open-source tools. A standard OpenAI-style API, so switching to us means changing an address, not a big integration project.

Phase 1 (fast-follow)

Fine-tuning-aware hardware choice new

The fine-tuning profiler and hardware chooser from section 06, built on the same measuring tools as inference. Less work than rollout serving, since the training frameworks already exist; Runara adds the measuring and choosing underneath them.

Phase 2

Per-step model & hardware routing hypothesis

If the harness tells us what kind of step each request is (planning, a tool call, summarizing), we send each step to a different model and hardware: a large model on fast hardware for planning, a small model on cheap hardware for routine helper work. Same idea, one level up.

Open decision

Connectors and the harness itself

Whether and when we build a harness is open. Oz: yes, step by step, starting with per-step routing. Adam: our current product is how we get in the door. The two views on connectors are in section 08. Not a priority for the current fundraise.

Next market

RL rollout serving

The same idea applied to training traffic: volume over speed, many answers per prompt, and a model that keeps changing. Part of the investor story now; built after inference and fine-tuning are proven.

12 Open risks

We start with sophisticated buyers

Enterprises without a harness will buy the bundle (ChatGPT Enterprise, Claude or Gemini in Workspace), and inference alone won't win them today. So the question for who we sell to now is: does this customer already have a harness? If yes, they're our market: coding-agent companies, AI-native startups, companies reselling tokens, GPU clouds serving agent traffic, and enterprise platform teams. If no, they're “not yet,” not “never.” Reaching them depends on whether we build a harness, which is still open.

Smart agent serving on its own is becoming free

NVIDIA Dynamo, llm-d, SGLang and LMCache already route by conversation memory and move it to cheaper storage, and funded startups sell memory-caching products. Sold on its own, this competes with free tools. Our edge is choosing the hardware, placing work by price, and showing measured results on the customer's own traffic, so we always pitch them together.

Fine-tuning's measurement burden is real new

For inference, standard GPU monitoring (NVML) gives detailed data every few milliseconds. For training, peak memory per step and delays from GPUs waiting on each other usually need hooks inside each training framework, or custom tools, to measure accurately across frameworks and setups. We should budget for this before promising profiling across all frameworks as a finished feature.
