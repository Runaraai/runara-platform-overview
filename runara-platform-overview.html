Runara Platform Overview

A short digest of three linked threads — how Runara serves harness traffic, whether "one API for every model" is a business we should build next to it, and the scale-out plan that gives both more clouds and real autoscaling. The last section puts every piece in one picture; full detail lives in the linked briefs.

01

Harness-Aware Serving

The product we're already building: a control plane that picks the cheapest hardware for a model, then serves harness traffic on it without redoing work already done.

  1. Two decisions, not one.

    The control plane chooses which hardware runs a model (cheapest chip/engine that meets the SLA) and separately runs harness-aware serving on top of it — session-aware routing, cache placement, burst-aware autoscaling. Most competitors only do one of these.

  2. The traffic is almost entirely cached prefill.

    Agent sessions run ~43 median turns, ~142K median input tokens, and a >96% observed prefix-cache hit rate. Software alone (cache-aware serving) moved revenue per gigawatt 1.8–2.7× on identical hardware in a published benchmark.

  3. v3 added two more harnesses, same thesis each time.

    Fine-tuning gets its own profiler (forward/backward/optimizer time & memory, LoRA/QLoRA, parallelism choice); RL rollouts get an architecture showing where rollout generation meets the training step. Both are "pick the cheapest hardware for this workload shape," one layer removed from inference.

  4. Staffing was sized generously, not leanly.

    ~20 engineers across all three streams plus cross-cutting roles (DevOps/Kubernetes, security/compliance for BYOC, a technical PM) — sized so a lean first hire isn't mistaken for the ceiling.

  5. Neutrality is the current moat.

    An OpenAI-compatible API means any harness switches to Runara by changing one base URL, and Runara doesn't compete with the harnesses it serves — today. Whether to grow into the harness later is still an open team decision.

02

OpenRouter, and our single-API question

The clearest existing proof that routing between models is itself a fundable, acquirable business — and what we found when we checked whether Runara is already one.

  1. The sharpest insight is in its own data.

    Anthropic captures ~46% of platform revenue on only ~12% of token volume — premium models monetize far above their traffic share; cheap open models drive the volume the public leaderboard advertises.

  2. Six decisions built the moat.

    Pass-through pricing, fast new-model integration, privacy as a feature (not a footnote), a public leaderboard flywheel, generous BYOK, and catalog breadth across both US and Chinese labs.

  3. Real, named risks.

    A thin take rate that open-source LiteLLM can undercut for free, standing provider-disintermediation risk, and the sharpest critique: the better it commoditizes model choice, the less valuable that commoditization becomes over time.

Are we already a single API? — checked, not assumed
  1. Short answer: not yet.

    No endpoint exists today where a caller sets model and Runara decides which hosted deployment or external provider answers it.

  2. What exists instead.

    playground/chat and console/chat are bring-your-own-endpoint proxies (caller supplies the endpoint); api/v1/models/deployments/workloads is a deployment-management REST API — neither is a model-routed single endpoint.

  3. The raw material is already there.

    discoverModelApi/chatModelError already do model-capability discovery and OpenAI-compatible error normalization — exactly the plumbing a router needs, just not assembled into one public endpoint yet.

  4. The near-term path is additive.

    One new endpoint, same shape as playground/chat but keyed on model instead of endpoint, routing to the optimizer catalog (Runara-hosted) or a provider passthrough table — not a pivot away from harness-aware serving.

  5. The differentiator if we build it.

    Runara-hosted replicas become "one more provider" in an OpenRouter-style table, except routed by measured cost-per-token from our own characterization work, not a provider's advertised list price.

04

Product architecture, everything combined

Sections 01–03 as one system. Requests travel down the left side, deploys and policy travel down the right, and every answer comes from the compute layer at the bottom.

Live today In build or on the roadmap Proposed, not started Badges: 01 harness-aware serving · 02 single API · 03 scale-out

How a request travels

  1. A harness calls the single API or the serverless gateway with its key.
  2. The gateway checks the key, queues the request and meters usage into Stripe.
  3. Harness-aware serving routes it to the replica that already holds the session’s cache.
  4. A hosted replica, a BYOC replica or an external provider answers.

How a deploy travels

  1. A tab hands the deploy to one pipeline.
  2. runara.ai picks the cheapest hardware that meets the SLA.
  3. The autoscaler creates the cluster or VM pool and sets min and max replicas.
  4. The in-cluster agent reports state back, and Convex stays the source of truth.
